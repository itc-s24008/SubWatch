- ブランチは、バグ1件（または同じ原因のまとまり）ごとに1本。名前は `fix/短い説明`（例：`git switch main && git pull && git switch -c fix/calendar-month-end`）。
- Pull Request は、テンプレート（`.github/pull_request_template.md`）を全部埋める。AIの利用の記録も書く。副担当の確認の後、すぐ main に入れる。
- 12/2 にテスト仕様書の異常系のケースとして行ったもののうち、コードのテストにできるものは、12/3〜12/9 のバグ修正の中で、その機能のテスト担当が自動テストのコードとして足す（`テスト_異常系の追加.md`）。

```
SubWatch のバグを直す。開発ルール（CLAUDE.md。内容は AGENTS.md と同じ）に従う。
バグ：（報告書の内容をそのまま書く：手順、期待、実際）
1. 設計書の該当箇所を読み、正しい動きを確かめる。
2. まず、このバグを再現するテストを書いて、落ちることを見せる。

4. 最小の修正をして、テストが通ることを見せる。ほかの箇所を直さない。
5. npm run typecheck、npm test、npm run test:emulator、npm run build の結果を、そのまま報告する。画面のバグのときは npm run test:e2e も実行する。
```

## 05-05：測定の道具を作る（創大。12/3 の前半3時間）

```
SubWatch の WBS 05-06 の非機能の測定に使う道具を作る。開発ルール（CLAUDE.md。内容は AGENTS.md と同じ）に従う。
最初に、機能設計書「テスト一覧」の No.60〜62 と、要件定義書の非機能要件を読む。
1. `tests/e2e/layout.spec.ts`：画面の幅を375pxにして、すべての画面を開き、`tests/e2e/helpers.ts` にある `expectNoHorizontalScroll(page)` と `expectTapTargets(page)` で確かめる。道具は作り直さず、今あるものを使う。テスト名に No.60 を入れる。
2. `scripts/seed-200.ts`（No.61 の準備。TypeScript）：API を200回呼ばず、Admin SDK（firebase-admin）で Firestore に直接200件入れる（無料枠の読み取り1日5万回を使い切らないため。API の登録は1回ごとに、上限と同名の判定のためにそのユーザーのサブスク〔最大200件〕を読む）。引数 `--email （テスト用アカウントのメールアドレス）`。サービスアカウントキーは環境変数 FIREBASE_SERVICE_ACCOUNT_JSON（Base64）から読む（tsx は 04-01 が devDependency に入れてある。無ければ package.json は変えずに報告して止まる。実行は人が `node --env-file=$HOME/secrets/cron.env --import tsx scripts/seed-200.ts --email …` で行う。AI は `~/secrets` を読まず、本番に向けて実行しない）。`getUserByEmail` で uid を求め、`users/{uid}` があることと、`users/{uid}/subscriptions` が0件であること（`limit(1)` で1回読む）を確かめ、どちらかが違えば止める。サービス名は「テスト 001」〜「テスト 200」のように毎回違う名前にし、各項目と作成日時などは DB設計書 2.テーブル定義書(No2) と API の登録と同じ形にする（足りない値は報告する）。ID は自動の ID（`collection().doc()`）にし、`subscriptionNotificationEnabled` は false にする（本番の Cron に通知を作らせないため。決まりの一覧 C-14）。各サブスクの nextBillingDate は `lib/billing.ts` の `nextBillingDate` で計算して入れる（このスクリプトだけは tsx を使って `lib/billing.ts` を import してよい〔ほかの scripts/ の .mjs は lib/ を読み込まない〕。式を書き写さない）。最後に `users/{uid}` の `subscriptionCount` を 200 にする（同じ batch で update する）。書き込みは batch（500件以下）で行う。実行前に、プロジェクトIDとメールアドレスを表示し、確認を受けてから始める。入れた件数を最後に表示する。Emulator で試すときは引数 `--emulator`（FIRESTORE_EMULATOR_HOST・FIREBASE_AUTH_EMULATOR_HOST を使う）を付ける。
3. 作る前に、作るファイルと推測が必要な箇所を一覧にして見せ、確認を受ける。アプリのコードは変えない。
4. npm run typecheck、npm test、npm run test:e2e の結果を、そのまま報告する。
```

- seed-200 には、サブスクが0件のテスト用アカウント（画面で登録して users があるもの）を使う（200件は1人の上限）。本番で実行するのは、サービスアカウントの鍵を `~/secrets/cron.env` に持つ創大（手順書 03 の 6）で、手順書 04 の「本番でスクリプトを実行しない」の例外。AI には実行させない。
