# 04-24：テスト仕様書を作る（創大。12/1 午後）

## AIに渡すプロンプト
```
SubWatch のテスト仕様書の下書きを作る。開発ルール（CLAUDE.md。内容は AGENTS.md と同じ）に従う。
機能設計書「テスト一覧」（No.1〜75。No.65〜75 は R15 の補足8 で足した）は、事前に作ったテスト計画である。今日は、それを手順と担当のあるテスト仕様書にする。テスト一覧と、各機能の詳細シートの受入条件・異常系を読み、全 Must 機能（F-01〜F-04・F-06〜F-08・F-10・F-12）と、作った Should（F-05・Web Push。削ったときは表から外す）について、表を作る。F-10 の検索・並べ替え（No.58）は Want なので、11/26 の予備（04-20）で作ったときだけ表に入れ、備考に「Want。成功基準①の判定から除く」と書く。
列：No.／機能／正常系・異常系／前提／手順（人が画面で行う手順）／期待する結果／担当（作った人と別の人）／実施環境（公開環境 or ローカル）／結果（空欄）／備考（空欄）。異常系は、詳細シートの「異常系」から機能ごとに1件以上のケースを全機能分入れ（04-24 で創大が書く。`テスト_異常系の追加.md`）、備考に「異常系の追加」と書く。各機能のテスト担当は 12/2 のテストの前に読む（テストの時間に含む）。12/2 の約20件の中で行う（自動テストのコードにするのは 12/3〜12/9 のバグ修正の中）。
担当（WBS 05-01〜05-03。1人20件程度〔異常系のケースを含む〕。人が画面で行うものは1件10分ほどで見積もる。単体テストと Emulator のテストの番号は、コマンドで実行する）：
- 05-01 星凪：創大の 請求日・Cron・通知・トライアル・検索（Want。11/26 の予備で作ったときだけ）
- 05-02 結愛：星凪の 登録・編集・削除の画面、カレンダー、詳細、S-11〜S-13 と、創大の 登録・編集・削除の API、アカウント削除（F-07）
- 05-03 創大：結愛の 認証・ホーム・一覧・Push・通知履歴・設定（No.60〜62 は 05-06 で測るので、ここには入れない。11/26 の予備で創大が 04-15〔Push 送信〕を作ったときは、その分だけ 05-01 の星凪がテストする）
本番の Cron は毎日9時台・11時台・18時台にだけ動き（Vercel の無料プランでは、決めた時刻から最大59分遅れる）、日付を指定できない。同じ日の通知は9時台の1回目で作られる（11時台と18時台は続きの処理だけ）。12/2 の Cron の確認は、2限の初め（10時以降）に行う（10時より前に cronRuns が無くても失敗としない。9時台の実行が partial や failed のときは、11時台の実行の後（12時以降）にもう一度見る。それでも残っていれば、18時台の実行の結果を次の授業日に見る）。再実行と日付指定の試験は「ローカル」にする。
テスト一覧に番号の無い細かい場面（Cron と同時の削除、削除の後片づけの3回、Push から開いて 404 なら S-08、S-06 の換算額、PATCH の約束、bootstrap の 409・500・やり直せる失敗〔503・500 RESOURCE_EXHAUSTED・409 CONFLICT・通信の失敗〕・登録済みメールの文、S-09 の「パスワードを再設定」、ログアウト後に戻るボタンで S-02、確認用パスワードの不一致、S-06 のトライアルの表示、入力項目の表〔要件定義書 共通ルール〕の行ごとの不正値、ダイアログの Tab・Esc・背景と PC の幅480px、ログイン済みのままの別の人のログインで Push 購読が外れること。テスト一覧 C79 の全部）も、ケースとして入れる（決まりの一覧 C-15）。
成功基準①は、このテスト仕様書の手動テスト（12/2）の結果で判定する（AI が書いた自動テストは補助。決まりの一覧 B-6）。
docs/テスト仕様書.md に書く。結果は書かない。
```

AIの使い方の記録：AIが作った下書きのどこを人が直したか（足した項目・消した項目・直した手順）を、`docs/テスト仕様書.md` の最後に「AIの使い方」として書く。

## 報告書の置き場所と形
報告書は、リポジトリの `docs/報告書.md` に1つだけ作る（12/2 の4限後半に星凪が取りまとめ、4限の終わりまでに結愛が「完成版」として出す。12/3〜12/9 の結果を追記し、12/9 に「追記版」として出す）。見出しは次の4つ。
1. テスト結果：テスト仕様書の No. ごとの結果（12/2 は、テストした人が直接書く）
2. 未実施：できなかった項目と理由（削った機能とその理由〔Must を削ったとき、測れなかった成功基準〔「未測定」と書く〕があるときは、12/9 の MVP の判定を「条件付き合格」とし、教員の判断を仰ぐ〕、端末がないなど）。後で行ったら結果を書き足す
3. 統合記録：`docs/統合記録.md` の要点（統合日ごとの結果、外したもの、削ったもの）
4. AIの使い方：AIに任せた所、人が直した所、AIの誤りとその見つけ方
