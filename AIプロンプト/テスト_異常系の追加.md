# 異常系テストを足す（12/1 に 04-24 で創大がテスト仕様書のケースを書き、12/2 に各機能のテスト担当が行う。12/3〜12/9 に自動テストのコード）

AIが書いたテストだけに頼らないため、異常系を1機能につき1件以上、テスト仕様書のケースにする。
- 12/1：04-24（テスト仕様書。`テスト仕様書_作成.md`）の中で、創大が全機能分の異常系のケースを書く（備考に「異常系の追加」と書く）。
- 12/2 のテストの前：各機能のテスト担当（作った人と別の人。WBS 05-01〜05-03）が、そのケースを読む（テストの時間に含む）。
- 12/2：そのケースを、約20件のテストの中で行い（1件10分）、結果を `docs/報告書.md` に直接書く。
- 12/3〜12/9：コードのテストにできるものは、バグ修正の中で自動テストのコードとして足す（下のプロンプト）。作った人のテストファイルは変えず、別のファイルに書く（例：`tests/emulator/account.extra.test.ts`、`tests/e2e/auth.extra.spec.ts`）。足したファイル名を Pull Request と報告書に書く。

## ブランチと入れ方（12/3〜12/9 に自動テストのコードを足すとき）
- 全機能が main に入っているので、main から `test/extra-04-xx`（xx はタスクの番号）を作る（例：`git switch main && git pull && git switch -c test/extra-04-17`）。
- Pull Request の base は main にする。作った人と別の人が確認し、すぐ main に入れる（12/2 以降の修正と同じ）。
- テストが落ちたら、コードは直さない。そのテストに `it.skip`（画面のテストは `test.skip`）を付け、理由をコメントに書く（例：`// 04-17 の不具合。期待：…、実際：…`）。Pull Request に書いて、作った人に知らせる。作った人が直したら、`it.skip` を外す。

## AIに渡すプロンプト
```
SubWatch の機能（機能名を書く。例：F-03）のテストを見直す。開発ルール（CLAUDE.md。内容は AGENTS.md と同じ）に従う。
1. tests/ の該当するテストと、機能設計書の詳細シートの「異常系」、テスト一覧を読む。コードはまだ読まない。
2. 設計書にあるのにテストされていない異常系を、一覧にして見せる。
3. 人が選んだものを、設計書の期待値のとおりにテストとして書く。作った人のテストファイルは変えず、`（機能名）.extra.test.ts`（画面は `.extra.spec.ts`）に書く。テストが落ちたら、コードは直さずに、そのテストを `it.skip` にして理由をコメントに書き、報告する（作った人が直す）。
```
