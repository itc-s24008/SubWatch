## 作るもの
- `app/api/cron/daily/route.ts`、`lib/cron.ts`、`lib/notifications.ts`（判定・決定的ID）
- `subwatch/vercel.json`（`設定ファイル/vercel.json.04-14で配置` をコピー。Root Directory が subwatch なので、この場所に置く）
- `scripts/trigger-cron.mjs`：Cron を手で実行する。`--reset` でその日の cronRuns を消す（11/25 のα版のデモで、公開前の Firebase プロジェクトに使う。実行前にプロジェクトIDを表示する。接続の値は、リポジトリの外の `~/secrets/cron.env` から `node --env-file=$HOME/secrets/cron.env scripts/trigger-cron.mjs` の形で読み、スクリプトの中に書かない。`FIREBASE_SERVICE_ACCOUNT_JSON` は Base64 の1行なので、`Buffer.from(値, 'base64').toString('utf8')` で戻してから `JSON.parse` し、Admin SDK の `cert()` に渡す（サーバーと同じ読み方）。リポジトリの中（`subwatch/.env.local` を含む）に本物の値を置かない。12/1 の公開後は使わない）。呼び先は引数 `--url https://（公開URL）` で渡す。`--reset` を付けたときは、今日（日本時間）の cronRuns（`cronRuns/{今日の日付}` の1件だけ）を消してから、Cron を1回呼ぶ。.mjs のスクリプトは `lib/` を import できないので、今日の日付を求める式は、このスクリプトの中に書いてよい（例外は 05-05 の `scripts/seed-200.ts` で、tsx を使って `lib/billing.ts` を読み込む）
- `tests/unit/notifications.test.ts`、`tests/unit/cleanup.test.ts`、`tests/emulator/cron.test.ts`。通知イベントを Firestore に直接置く `seedNotificationEvents(uid, items)` と、Cron を呼ぶときのヘッダーを作る `cronAuthHeaders()` を `tests/emulator/helpers.ts` に足す（04-21 も使う）
- refresh_stale（古い nextBillingDate の更新。詳細_F-06 の手順4）の update は、1件ずつ、検索で読んだ文書の `updateTime` を前提条件に付けて行う（`doc.ref.update(data, { lastUpdateTime: doc.updateTime })`）。読んだ後に利用者が編集したサブスク（gRPC の code 9 FAILED_PRECONDITION）は、消えたサブスク（code 5 NOT_FOUND）と同じく無視し、failedCount に数えない（利用者の編集を、古い請求日から計算した値で上書きしないため。決まりの一覧 C-8）。この重なりの自動テストは作らなくてよい
- Push の送信は `lib/types.ts` の PushSender を引数で受け取る（`lib/push.ts` を import しない。テストでは偽物を渡す。つなぐのは 11/25 の統合）。テスト No.43 は続きから処理する部分
- 通知イベントの作成は、親の users/{uid} とその通知イベントを読む transaction の中で行う（詳細_F-06 の手順7。users/{uid} が無くなっていたら作らない。アカウント削除と同時に動いても、持ち主のいない通知を残さないため）。Emulator のテストに「通知を作る直前に users/{uid} が消えたら作らない」を1件入れる
- Cron と PushSender の分担（型定義のコメントのとおり）：Cron が行うのは、送る通知イベントを選ぶ、締切（240秒）を確かめる（利用者ごとの前と、通知イベントを1件送る前の両方。過ぎていたら、そこで止めて partial で終える。残りは次の実行（11時台・18時台）が続ける）、PushSender を呼ぶ、戻り値の status で sentCount（sent・partially_sent）と failedCount（failed）を数える、まで。購読の読み取りと削除、通知イベントの webPushDeliveredIds・webPushStatus・webPushSentAt・webPushLastErrorCode の保存は PushSender（04-15）が行うので、Cron では書かない。PushSender が例外を投げたときは、その実行を failed にする（手順12）
- 11/25 の統合までは、route は「何も送らず、何も保存せずに skipped を返す仮の PushSender」を渡す。統合で、04-15 の `lib/push.ts` が export する `pushSender` に差し替える（1か所）。route を通すテストでは、通知イベントの webPushStatus を期待値に入れない（統合で本物の送信に替わると、購読の無い利用者は pending ではなく skipped になる）。送信の結果を確かめるテストは、`runDailyCron` に偽の PushSender を渡して行う
- `tests/unit/cleanup.test.ts` は、繰り返しの判定（500件に達したら続ける、最大10回、締切で止める）を確かめる。削除そのものは Emulator のテストで確かめる
