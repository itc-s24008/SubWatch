# 確認チェックリスト（AIの報告を人が確かめる）

AIの「できた」は信じず、自分で実行して確かめる。

## Pull Request を出す前（担当者）
| # | 確認 | 方法 |
|---|---|---|
| 1 | 型検査が通る | `npm run typecheck` |
| 2 | 単体テストが通る | `npm test` |
| 3 | Emulator と画面のテストが通る | `npm run test:emulator`、`npm run test:e2e`（`NEXT_PUBLIC_USE_MOCKS` を消してから。動いている `npm run dev` と Emulator を止めてから） |
| 4 | ビルドできる | `npm run build`（秘密の値を表示しない） |
| 5 | 秘密の値がコードに無い | 表の下の「秘密の値の確認」の2つのコマンドが、鍵を出さない |
| 6 | ブラウザに Firestore が無い | リポジトリの直下で `git grep -n "firebase/firestore" -- subwatch/app subwatch/components subwatch/lib` が何も出さない |
| 7 | 共通ファイルを変えていない | `git fetch && git diff --name-only origin/main...HEAD` を `CLAUDE.md` の一覧と比べる（前のブランチから作ったときは、`origin/main` を `origin/（前のブランチ）` にする） |
| 8 | 設計書と同じ文言・見た目 | 設計書の図と並べて比べる |
| 9 | テストの期待値が設計書と同じ | テストを読む。AIが、コードに合わせて期待値を変えていないか |
| 10 | 仮に書いた所を伝えた | 仮の関数、仮の方法で操作したテストを、`docs/不足メモ/` と Pull Request の「統合のときに直してほしい所」に書いた |

### 秘密の値の確認（リポジトリの直下で。人が自分のターミナルで実行する）
次のコマンドは、AIに実行させない（`adminsdk` を含むので、AIの設定の禁止ルール `Bash(*adminsdk*)` で止められる）。人が自分で実行して、結果を見る。
```bash
git -c core.quotePath=false ls-files | grep -iE '(^|/)\.env($|\.)|cron\.env|key|secret|vapid|adminsdk' | grep -v '\.example$'
git grep -nE 'eyJ0eXBlIjoic2VydmljZV9hY2NvdW50|ewogICJ0eXBlIjogInNlcnZpY2VfYWNjb3VudCIs|BEGIN PRIVATE KEY|"private_key": "-----BEGIN|FIREBASE_SERVICE_ACCOUNT_JSON=.|VAPID_PRIVATE_KEY=.|CRON_SECRET=.' -- . ':!*.example' ':!AIプロンプト' ':!手順書'
```
1つ目は、名前に key・secret・vapid などを含むファイル（`.example` を除く）を出す。出たら中身を確かめ、鍵でなければよい。2つ目は何も出ないこと。

## 副担当の確認（5分の口頭確認。質問は固定。画面や API の無いタスクは、1の代わりに、そのタスクの「人が確かめること」の説明の項目を聞く）
1. この機能の、画面→API→DB の流れを説明してください。
2. 失敗したときは、どう動きますか？（例を1つ）
3. このテストは、何を守っていますか？（1つ選んで）

答えられないときは、担当者がコードを読み直してから、もう一度確認する。結果を Pull Request に記録する。

副担当は、異常系テストを足さない（確認の0.5時間は、読むことと5分の口頭確認・記録だけ）。異常系は、12/1 のテスト仕様書（04-24）に創大が全機能分のケースとして書き、その機能のテスト担当が 12/2 のテストの前に読んで、約20件の中で行う。自動テストのコードとして足すのは 12/3〜12/9 のバグ修正の中（`テスト_異常系の追加.md`）。
