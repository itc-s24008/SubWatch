# 05 Pull Request と統合（全員）

## 1. ブランチ
- タスクごとに1本。名前は `AIプロンプト/` の各ファイルに書いてある。
- main に直接 push しない（GitHub の無料プランの Private リポジトリでは、ブランチの保護ルールが効かないので、3人のチームのルールとして守る。例外は、反映が止まったときに星凪が push する `subwatch/` の中の1行の変更だけ。手順書 02 の 3・6）。
- 同じファイルをほかの人が直しそうなときは、作る前に声をかける。
- 04-01 と 04-04 は、ほかのタスクが使うので、確認のあとすぐ main に入れる（04-01 の段階1〜2 は 11/12 の4限のうちに。段階3〜4 は 11/17 の2限の終わりまでに Pull Request を出し、3限の初めの30分で星凪が確認してマージする。04-04 は 11/17 の4限の最後の30分に読み、11/18 の1限の最初の30分に口頭確認とマージ〔下の 5〕）。04-05・04-06 も、11/18 の1限の最初の30分にマージする（11/18 にマージするのは 04-04・04-05・04-06 の3本。11/19 の統合①の範囲には入らない）。04-17 は 04-21 と同じファイルを触るので、11/25 の4限に結愛が確認し、11/26 の1限の初めに星凪が入れる（入っていないときは決まりの一覧 B-9）。ほかは統合日に入れる。
- 同じ人の続きのタスク（04-05→04-09、04-06→04-08、04-12→04-15）は、前のブランチから作る。Pull Request の base も前のブランチにする（副担当に、そのタスクの差分だけが見える）。
- 12/2 以降の修正（05-xx）は、副担当の確認の後すぐ入れる。バグ修正のブランチ名は `fix/短い説明`（`AIプロンプト/バグ修正.md`）。
- `docs/不足メモ/` はタスクごとに別のファイルにする。`docs/統合記録.md` は、まとめ役だけが書く（例外：11/18 の Deploy Hook の確認の結果は星凪が書く）。統合日以外に書くときも、main へ直接 push せず、ブランチ（例：`docs/integration-record-1112`）を作って書き、Pull Request で入れる。

## 2. 共通ファイルを変えたいとき
1. 自分のタスクの中では変えない（一覧は開発ルール `CLAUDE.md`）。
2. 創大に相談する。
3. 共通ファイルだけの Pull Request を出し、先に main に入れる。
4. 3人が `git pull` する。自分のブランチに `git merge main` する。

## 2-2. 開発ルール（CLAUDE.md）を直すとき
共通ファイルと同じく、創大に相談し、CLAUDE.md だけの Pull Request にする。直したら、同じ内容を AGENTS.md にもコピーし、大きさを確かめる（決まりの一覧 D-4。28,000 バイト以下。足すときは、同じだけ削るか、細部を `docs/開発ルールの詳細.md` へ移す）。`設定ファイル/CLAUDE.md` も同じ内容にそろえる。`docs/開発ルールの詳細.md` を直したときは、`設定ファイル/開発ルールの詳細.md` にもコピーする。
```bash
cp CLAUDE.md AGENTS.md && cp CLAUDE.md 設定ファイル/CLAUDE.md
wc -c CLAUDE.md AGENTS.md    # どちらも同じ大きさで 28000 以下
cmp CLAUDE.md AGENTS.md && echo OK    # OK と出ればよい
```

## 3. 仮データ
相手の機能が未完成の間は、`.env.development.local` に `NEXT_PUBLIC_USE_MOCKS=true` を足す。`lib/api-client.ts` が `subwatch/mocks/index.ts` の値を返す。統合のときに、この行を消して本物の API で確かめる。画面のテストは仮データを使わない（`CLAUDE.md`）。

## 4. Pull Request
1. `AIプロンプト/確認チェックリスト.md` の「出す前」を確かめる。
2. push して Pull Request を作る。テンプレートを全部埋める（AIの利用の記録を含む）。
3. 副担当に頼む。

## 5. 副担当の確認
1人が1日に持つ主タスクは1つ、副担当も1つまで（11/12 以降のタスク。例外は 11/17 で、創大は 04-01 の残り〔1〜2限。段階3〜4。3時間〕と 04-04〔3〜4限。2.5時間〕の2つ、星凪は 04-02 の初回デプロイ〔2限。0.5時間〕と 04-06 の2つを持つ。創大の2つの確認は星凪がまとめて行う〔星凪の 04-06 は4.5時間で終わる大きさ〕。11/17 の結愛は 04-06 と 04-02 のデプロイ〔公開URLでログイン画面が開くことを見るだけ〕、創大は 04-05 の副担当）。初回デプロイでは、結愛は 04-05 の途中で10分抜けて、自分のパソコンでサービスアカウントの鍵を貼り、星凪が作った Deploy Hook の URL を写す（叩くのは 11/18。手順書 02 の 4 の B）。開発日の各タスクの6時間は、主タスク5.5時間と、副担当の確認0.5時間（1件。読むことと5分の口頭確認・記録だけ。予備の枠も同じで、作業は5.5時間）と数える。統合日は、午前3時間が全員の統合で、午後3時間のタスクの中に副担当の確認0.5時間を含める（午後のタスクは2.5時間で終わる大きさ）。まとめ役の午後の副担当の確認は、その日の「統合の残り」の時間の中で行う。副担当は `AIプロンプト/README.md` の表（04-01 は 11/12 の分が結愛・11/17 の分が星凪、04-02 は 11/12 の分が創大・11/17 のデプロイが結愛、04-03 と 04-22 は星凪、05-07 は結愛、05-08 は創大）。予備で作る作業の副担当は、その日の予備の枠の副担当（決まりの一覧 A-3・B-5）。
1. コードを読む。分からないところは聞く。
2. 5分の口頭確認（質問は3つ）：画面→API→DBの流れ／失敗時の動き／このテストが守るもの。
3. 答えられなければ、読み直してから、もう一度行う。
4. 結果を Pull Request に書く。
5. 異常系のテストは、ここでは足さない。12/1 のテスト仕様書（04-24）に、創大が全機能分の異常系のケースを書き、各機能のテスト担当（作った人と別の人）が 12/2 のテストの前に読んで（テストの時間に含む）、約20件の中で行う。自動テストのコードとして足すのは、12/3〜12/9 のバグ修正の中（`AIプロンプト/テスト_異常系の追加.md`）。
6. このあと、担当者は動作見本と比べてよい（結愛のパソコンで、結愛と一緒に見る）。違いがあれば、設計書と照らして、必要なら直す。

**11/17 の4限の最後の30分：** 3人とも「Pull Request を読んで、気づいたことを書く」だけの枠（創大は 04-05、結愛は 04-06、星凪は 04-04）。

**11/18 の1限の最初の30分：** 口頭確認3本とマージ（04-04・04-05・04-06 の3本）と Deploy Hook の確認だけを行う（3本×5分＋マージ。星凪がマージする。決まりの一覧 B-9）。11/17 に休んだ人の残り（初回デプロイ・鍵・Deploy Hook の作成）は、ここでは行わず、11/18 の4限の最後の30分に行う。11/18 の主タスク（04-07・04-08・04-09）は、この30分を引いた5時間で終わる大きさ。30分の終わりに Deploy Hook の確認を行う：3本のマージの後で main の `npm run build` が通ることを確かめてから、結愛が自分で作った小さな Pull Request（`subwatch/` の中の1行）を星凪が読んでから、結愛がマージし、Deploy Hook を叩く。星凪が Vercel の画面で、そのコミットが本番に出たかを見て、結果を `docs/統合記録.md` に書く（まとめ役の代わりに星凪が書いてよい。ブランチと Pull Request で入れる〔1〕。手順書 02 の 5-2）。

## 6. 統合日（午前2コマ）
1. まとめ役が `AIプロンプト/統合_統合日の共通.md` を使い、ぶつかりそうな箇所とマージの順番を出す。
2. 全員で順番を決める。
3. まとめ役が、統合用のブランチを main から作る（例：`git switch main && git pull && git switch -c integration-1119`）。この上に、1本ずつマージする（AI がローカルで `git merge` する。GitHub の Pull Request のボタンは、ここでは押さない）。作った本人が立ち会う。続きのブランチは、親 → 子の順に、別々に入れる。
4. 1本ごとに `npm run typecheck`、`npm test`、`npm run test:emulator`。全部入れたら `npm run build`、`npm run test:e2e`。
5. 全部入れたら、完了条件（WBS）を画面で確かめる。
6. `docs/統合記録.md` に記録する。
7. 統合用のブランチを push し、main への Pull Request を1本出す。3人で読んでから、星凪がマージボタンを押す（「Create a merge commit」。Squash にしない。各自のコミットを残すため。手順書 02 の 6）。星凪が休んだ統合日は、結愛がマージボタンを押し、Deploy Hook を叩いて本番に反映する（手順書 02 の 5-2。Deploy Hook の確認が通っていないときは、11/25 のデモはローカル〔Emulator〕で行い、12/1 は公開を 12/3 に延ばす）。公開環境で確かめる完了条件（11/25）は、このデプロイの後に確かめる。
8. 各自の Pull Request が、マージ済みになったことを確かめる。なっていないもの（続きのブランチなど）は、統合の Pull Request の番号を書いて閉じる。3人が `git switch main && git pull` する。
