## 1. requireAuth の分け方
- `requireAuth` は、ID token の検証（firebase-admin の `verifyIdToken`）の失敗を、エラーの code で次のとおりに分ける。表にない失敗を 401 にしない。

  | 返すもの | firebase-admin のエラー |
  |---|---|
  | 401 UNAUTHENTICATED | token が無い（Authorization が無い・`Bearer ` でない。verifyIdToken を呼ぶ前に返す）、`auth/argument-error`（形が違う）、`auth/id-token-expired`、`auth/id-token-revoked`、`auth/user-not-found`、`auth/user-disabled` |
  | 503 TEMPORARILY_UNAVAILABLE | それ以外のすべて（通信の失敗、`auth/internal-error` など。Auth の一時的な障害）。Firestore の UNAVAILABLE も 503 |

  `auth/user-not-found`・`auth/user-disabled` が出るのは `checkRevoked: true` の所（bootstrap と DELETE /api/account）だけ。503 では画面はサインアウトしない（`isGateError` は false。`LoadError` などの共通の文「一時的に利用できません」）。無料枠の超過は 500 RESOURCE_EXHAUSTED。

## 2. テストの道具と書き方
- `tests/emulator/helpers.ts`：`signUp()` → token、`uidOf(token)`、`callRoute(handler, options)` → `{ status, body }`（値は `body.data`。options は helpers.ts のコメント）、`seedUser(uid, fields?)`、`resetEmulators()`、`signUpUser()` → `{ uid, email, password, token }`。後のタスクが足す道具：`seedSubscriptions(uid, items)`・`TEST_DATA_SUBSCRIPTIONS`（テストデータの5件。04-07）、`seedPushSubscription(uid, fields?)`（04-12）、`seedNotificationEvents(uid, items)`・`cronAuthHeaders()`（04-14）。
- `tests/e2e/helpers.ts`：`loginAsNewUser(page, { initialized = true } = {})`（画面を通さずログイン済みにする。方法は、04-01 が E2E の口〔`window.__SUBWATCH_E2E__`〕に置く `signIn(email, password)` を /terms で呼ぶ。`false` なら users を作らない）、`await mockApi(page, method, path, responses)`（応答を順番に返し、`{ calls(), bodies() }` を返す。応答の形・`delayMs`・`'noResponse'`・クエリなどは `mockApi` の上のコメント。04-01）。ほかの道具：`callApi(page, path, options)`、`createUser()`、`waitForHydration(page, selector = 'form')`、`accountResponse(email, fields?)`、`expectNoHorizontalScroll(page)`・`expectTapTargets(page)`。
- 今日で変わる表示（解約案内、カレンダーなど）の画面のテストは、ログインの前に `page.clock.setFixedTime(…)` で今日を決める（固定されるのはブラウザの `Date` だけ）。サーバーが計算する値（nextBillingDate）と、それで決まる S-04 の既定の並び（並べるのは画面）は、`mockApi` の応答で決める。S-06 の解約案内は画面が計算するので、`mockApi` の nextBillingDate・trialEndDate と `page.clock` の今日の両方で決める。固定日（基準日 2026-11-04）の検証は、lib の関数を直接呼ぶテストで行う。`role="alert"`・`role="status"` は `main` の中だけを数える。
- Push の画面テスト（No.63・64）は、`page.addInitScript` でブラウザの `pushManager` を差し替え、偽の購読を返す。サーバー側の 503 の検証は単体テストで行う（画面テストと分ける）。
- 決まりの分岐のテストを入れる：S-01 の 503 の後の再押下で bootstrap だけが呼ばれる（04-05。テスト一覧 No.17 の「あわせて」）／削除の応答が届かないとき（通信の失敗と30秒の時間切れの2件）の Push 購読の解除・文・S-02（04-17）／購読が無い端末ではログアウトで DELETE /api/push/subscribe を呼ばない（04-12）。
- lib の差し替え口（テストで外から渡せるようにする所）：Push の送信関数（`PushSender`）、現在時刻、`verifyIdToken`、Cron の締切。
- F-13 が入った後は、`loginAsNewUser` を使わない画面のテスト（画面から登録する通しのテストなど）は、最初に `mockFavicon(page, 'failure')` を呼ぶ（本物の favicon.im へ通信しない）。
- Gates は、ログインした人ごとに最初に1回 GET /api/account を読む。画面のテストで GET /api/account を `mockApi` で作るときは、1つ目の応答を Gates が使うので、規約の版（`.env.development.example` の値）の入った正常な応答（`accountResponse(email)` で作れる）を先に置く。
- 画面のテストは仮データ（`NEXT_PUBLIC_USE_MOCKS`）を使わない。Emulator でログインし、まだ無い API や失敗の場面は `mockApi` で応答を作る。統合のあとも同じテストが動くようにするため。
- テスト一覧にある項目は、テスト名に番号を入れる（土台の確認のテストは番号なしでよい）。No.41（空・読み込み失敗・オフライン）は、ページ（`page.tsx`）を作る人が、その画面のテスト（ファイル名はプロンプト）に読み込み失敗を1件以上入れる（読み込みの無い S-05 の新規は、保存の通信失敗で代える）。
- 削除の30秒の時間切れ（`timeoutMs`）は `setTimeout` と `AbortController` で作る（`AbortSignal.timeout` は使わない。画面テストで `page.clock` を進めて確かめるため。決まりの一覧 C-14）。タイマーは `api()` の中で fetch を待つ前に作る。テストは、ページを開く前に `page.clock.install()` を呼び、`mockApi` の `calls()` で要求が届いたのを待ってから `page.clock.runFor(30_000)` で進める（届く前に進めると、まだタイマーが無い。決まりの一覧 C-9）。
- テスト一覧の No.65〜75（決まりの一覧 C-15）は、その機能を作るタスクが書く（番号の割り当ては各プロンプト）。C-4 の分岐と C-11 の「同時に2回で1件のまま」「acceptedAt と termsAcceptedAt が同じ値」は、番号なしのテストとして足す。

## 3. 測定とテストデータ
- 200件のテストデータ（No.61。`scripts/seed-200.ts`）は、API の登録と同じ項目にし、ID は自動の ID（`collection().doc()`）、`subscriptionNotificationEnabled` は false にする（本番の Cron に通知を作らせないため。決まりの一覧 C-13・C-14）。
- Cron の実行時間（成功基準⑤）は、cronRuns の `startedAt` と `finishedAt` の差で測る（Vercel のログは短い時間しか残らない）。200件のデータを入れた状態で測る（この200件は通知オフなので、通知の作成と Push の送信の時間は含まない。決まりの一覧 C-14）。
