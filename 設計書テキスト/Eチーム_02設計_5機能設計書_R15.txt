A17=用語 | B17=transaction：複数の読み書きを、全部成功か全部取り消しのどちらかにするFirestoreの仕組み。
決定的ID：同じ材料（uid・サブスク・種類・日数・送信日）から、いつでも同じIDを計算する方法。同じ通知は2件作られない。
sha256：文字列から固定の長さの値を計算する方法。決定的IDに使う。
冪等：同じ処理を2回実行しても結果が変わらないこと。
collectionGroup：同じ名前のコレクションを全ユーザー分まとめて検索するFirestoreの機能。インデックスが必要。
count()：ドキュメントを読まずに件数だけを数えるFirestoreの機能。
HTTP 204：「成功したが、返す内容は無い」という応答の番号。
auth_time：ID tokenに入っている、最後にパスワードで本人確認した時刻。
checkRevoked：ID tokenの検証で、削除・無効化されたアカウントかまで確かめる指定。
VAPID：Pushを送るサーバーを証明する鍵の組。
Service Worker：画面を閉じていてもPushを受け取るためにブラウザの中で動くプログラム。
gRPCコード：FirestoreのSDKが返すエラーの番号。
TTL：Firestoreが期限切れのデータを自動で消す機能。課金が必要なため使わない。
refresh_stale：Cronの最初の段階。古くなった次回請求日を計算し直す。
cleanup：Cronの最後の段階。期限切れの通知とCronの記録を削除する。
recursiveDelete：ドキュメントを配下ごと消す Admin SDK の機能。
基準日：テストで「今日」とみなす日。
A18=実装の注意 | B18=次は動作見本で確かめた内容（環境や版によって変わることがある）。
・typescript は 5系を使う（7系は Next 15.5 のビルドが失敗した）。
・Next 15 では route handler の第2引数 params は Promise（await して使う）。各route.tsに export const runtime = 'nodejs'; export const dynamic = 'force-dynamic'; を書く。
・route.ts からは、HTTPメソッドの関数と route segment config（runtime・dynamic・maxDuration など）以外を export しない（Nextのビルドが失敗する）。
・並行して複数のEmulatorを動かすときは、ポートを変えた firebase 設定ファイルを別に用意してよい。
・削除を伴うテストでは、偽の時刻（Dateの差し替え）を使わない（recursiveDelete が止まる）。
・Auth Emulator は checkRevoked=false でも常に失効を確認するため、『通常のAPIは失効を確認しない』ことはEmulatorでは確かめられない（bootstrapの失効→401は確かめられる）。
・Auth Emulator は、アカウント作成より前の auth_time を失効（401）として扱う。本番の Firebase で auth_time の5分判定がどう動くかは、実際の環境で確かめる。
・試し実行の3回目（11/06。設計書は R12 の版）の後に R13〜R15 で足した仕様（S-13 からのアカウント削除、401 と 503 の分け方、削除の応答が届かないときの扱い、consentHistory、30秒の時間切れ、navigator.onLine の判定、S-01 のやり直しの画面、seed-200.ts、テスト No.65〜75 など）は、AI で作って動かしていない（未検証）。
